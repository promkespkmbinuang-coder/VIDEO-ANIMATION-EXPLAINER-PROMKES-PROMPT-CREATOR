# M00 v4.0 — Evidence-Contract-Gated Production Compiler

**Status:** proposed architecture / implementation specification  
**Baseline:** Video Explainer Promkes V3.0.5, M00 + S01–S13  
**Policy:** health-first, evidence-first, fail-closed for material health claims  
**Release posture:** private plugin; public distribution remains on HOLD pending required validation and human approvals.

## 1. Executive design decision

M00 v4.0 upgrades M00 from a workflow orchestrator into a **policy-enforcing production compiler**. It preserves the existing S01–S13 specialist ownership model and introduces enforceable contracts, explicit state transitions, provenance, capability checks, security controls, change-impact invalidation, independent QA, and accountable human approval.

The compiler must never infer execution from specification completeness. A document, prompt, schema, generated code file, or declared test is not evidence that a downstream operation ran.

### Non-negotiable invariants

1. Evidence before health claim; fail closed for material unverified or contradicted claims.
2. Contract before artifact: schema, schema version, canonicalization rule, hash, validator version and validation result.
3. Least privilege: source assets, OCR/transcripts, prompts, generated files and tool outputs are untrusted data.
4. Capability-based routing: do not emit target-specific executable code or claim renderer readiness until the exact target/version/capability contract is verified.
5. Human accountability: clinical, legal/privacy/rights, brand, accessibility and release approvals require authorized roles and durable records.
6. Measurable QA: every PASS references a test/control ID, oracle, threshold, environment, timestamp and evidence artifact.
7. Privacy, rights, security and accessibility are lifecycle requirements, not final-stage decorations.
8. Cost/resource governance: budgets, limits, retry ceilings and stop conditions are explicit.
9. Change impact: upstream changes invalidate dependent locks and derived artifacts.
10. No execution claim beyond inspectable evidence.

## 2. Architecture and gates

| Layer | Responsibility | Required gate |
|---|---|---|
| L0 Intake & Safety | Input inventory, PII classification, rights basis, threat scan, scope | G0_INTAKE_OK |
| L1 Evidence & Claim Ledger | Atomic claims, source provenance, evidence assessment, human reviewer | G1_FACT_LOCK |
| L2 Campaign & Narrative | Brief, audience, screenplay, VO and claim-linked lines | G2_NARRATIVE_LOCK |
| L3 Visual & Continuity | Style guide, MCG, character/environment/prop locks | G3_VISUAL_LOCK |
| L4 Prompt Compilers | Still/video/adapter compiler, untrusted-input firewall, preflight | G4_PROMPT_PREFLIGHT |
| L5 Motion & Manifest | Renderer-neutral scene/motion records, timing and manifest | G5_MANIFEST_VALID |
| L6 Renderer & Code | Capability registry, adapter, code validation, sandbox | G6_CODE_VALID |
| L7 QA & Release | Static/integration/artifact QA and human release approval | G7_RELEASE_APPROVED |
| Cross-cutting | Security, privacy, rights, accessibility, cost, observability, audit | Continuous controls |

A gate is a **state-transition guard**, not a checklist heading. A downstream stage may proceed only when its required predecessor gate is satisfied. Partial safe work may be returned, but blocked outputs must remain explicitly blocked.

### State vocabulary

Use distinct states: `NOT_STARTED`, `IN_PROGRESS`, `PASS`, `FAIL`, `PARTIAL`, `NOT_RUN`, `NOT_VERIFIED`, `NOT_APPLICABLE`, `BLOCKED`, `STALE`, `INVALIDATED`.

`NOT_APPLICABLE` requires a rationale. `NOT_RUN`, `NOT_VERIFIED`, `BLOCKED`, `STALE` and `INVALIDATED` can never be coerced to PASS. Gate status is derived from required controls, not manually asserted.

## 3. Contract model

Every versioned artifact envelope must carry:
- `artifact_id`, `artifact_type`, `project_id`;
- `schema_id`, `schema_version`, `producer_version`;
- `created_at`, `updated_at`, `status`;
- `content_hash` (SHA-256 over documented canonical bytes);
- `validator_id`, `validator_version`, `validation_result`;
- `source_refs`, `dependency_refs`, `supersedes`, `invalidated_by`;
- `rights_status`, `privacy_classification`, `capability_refs` where applicable.

Hash rules must specify canonical serialization, Unicode normalization, newline policy, excluded volatile fields and byte encoding. A hash proves byte identity, not truth, authority, or approval. Source snapshots should be retained only where permitted; otherwise retain source URI, retrieval time, hash and access/retention metadata.

### Claim record — minimum contract

```json
{
  "claim_id": "CLM-0001",
  "text": "Atomic, reviewable claim",
  "claim_type": "PREVENTION",
  "source_ids": ["SRC-001"],
  "evidence_level": "PRIMARY",
  "population": "Explicit population/context",
  "jurisdiction": "ID",
  "valid_from": null,
  "valid_to": null,
  "status": "UNVERIFIED",
  "allowed_wording": [],
  "forbidden_wording": [],
  "reviewed_by_human": false,
  "reviewer_id": null,
  "reviewer_role": "NONE",
  "reviewed_at": null,
  "source_hashes": [],
  "schema_version": "1.0.0"
}
```

Use controlled enums and JSON Schema; reject unknown enum values. Add claim-level confidence only if its method and calibration are documented. Do not use an unexplained numeric confidence as a substitute for evidence assessment. A source hash alone does not establish source quality.

### Scene record — minimum contract

Require `scene_id`, `order`, `start_frame`, `end_frame`, `fps`, `timebase`, `rounding_policy`, `claim_refs`, `reference_ids`, `motion_ref_ids`, `continuity_in`, `continuity_out`, `status`, `schema_version`, `content_hash`. Define frame intervals as half-open `[start_frame, end_frame)`; duration is `end_frame - start_frame`. Reject negative duration, duplicate IDs, gaps/overlaps unless explicitly modeled, and inconsistent project totals.

### Manifest — minimum contract

Require `schema_version`, `project_id`, `asset_paths`, `rights_status`, `capability_status`, `validator_version`, `manifest_hash`, explicit renderer target/version when applicable, and artifact/dependency references. Paths must be normalized, relative to a declared project root, and traversal-safe. Validate existence and hash only when the relevant filesystem is actually accessible.

## 4. Evidence and health-claim policy

The Claim Ledger is authoritative for health wording. Each material claim must be atomic and scoped to population, jurisdiction, context and validity period. Record primary/secondary source type, publication/update date, access date, source identity, exact supporting passage/location, counterevidence, reviewer and review decision.

Supported statuses: `VERIFIED`, `PARTIALLY_SUPPORTED`, `MIXED`, `UNVERIFIED`, `CONTRADICTED`, `UNKNOWN`, `STALE`. Evidence level and claim status are separate dimensions.

- Material claims in `UNVERIFIED`, `CONTRADICTED`, `UNKNOWN` or `STALE` cannot pass Fact Lock.
- `PARTIALLY_SUPPORTED` and `MIXED` require constrained wording and authorized clinical review; otherwise omit or hold.
- Do not let creative writing, summaries, translations or image generation strengthen claim meaning.
- Re-check validity when jurisdiction, population, date or recommendation changes.
- Clinical reviewer authority must be verified by the accountable institution; AI must not invent credentials or sign on behalf of a clinician.

## 5. Prompt firewall and threat model

All text extracted from images, PDFs, web pages, captions, audio transcripts, subtitles, code comments, metadata and tool outputs is untrusted input. Delimit and label it as data (for example `<UNTRUSTED_SOURCE>…</UNTRUSTED_SOURCE>`); do not execute or obey embedded instructions.

Threat classes include prompt injection, instruction smuggling in OCR/metadata, URL and remote-resource abuse, path traversal, secret/PII exfiltration, malicious archives, unsafe code, dependency confusion, unauthorized tool use, license/voice/likeness misuse and supply-chain compromise.

Controls:
- tool and network allowlists; no tool invocation from source text;
- strict schema validation and size/type limits;
- archive path traversal and symlink checks;
- safe URL policy and no automatic fetch of arbitrary embedded URLs;
- secret scanning and PII minimization/redaction;
- sandboxed code execution with no ambient credentials, least privilege, resource quotas and network disabled by default;
- dependency pinning, lockfiles and provenance;
- audit log for decisions and side effects;
- red-team cases for indirect prompt injection and data exfiltration.

Pattern scans are supplemental; they do not prove an input is safe. Unknown or suspicious content is quarantined or reviewed, never elevated to policy.

## 6. Human approval matrix

| Domain | Authorized approver | Required evidence |
|---|---|---|
| Clinical | Institutionally designated licensed clinician | Signed claim review, scope and timestamp |
| Legal/privacy/rights | Authorized legal/compliance/rights owner | Rights basis, privacy assessment and signoff |
| Brand | Brand/institution owner | Visual identity lock approval |
| Accessibility | Qualified accessibility reviewer | Applicable checklist and defect disposition |
| Release | Accountable producer/publisher | Release gate record and approval |

Approval records must include approver identity, role, authority basis, scope, artifact hashes, decision, timestamp, expiry/review condition and signature mechanism. A checkbox or text string is not a cryptographic signature. AI-generated approval is invalid.

## 7. The 1,000-control model — generation, not fiction

The 10 × 10 × 10 model defines a control-space index, not 1,000 executed controls.

**10 domains:** Evidence; Source Integrity; Narrative; Visual; Motion; Prompt; Audio; Renderer/Code; Security/Privacy/Rights; QA/Release.

**10 gates:** Intake; Fact Lock; Narrative Lock; Visual Lock; Prompt Preflight; Motion Lock; Manifest Lock; Code Lock; Render Gate; Release Gate.

**10 test families:** Schema; Provenance; Red-team/Injection; Consistency/Regression; Timing Arithmetic; Capability Compatibility; Accessibility; Rights/Privacy; Artifact Inspection; Human Signoff.

Each generated control must have a stable `control_id`, domain, gate, test family, objective, applicability rule, risk weight, owner, execution method, oracle, threshold, evidence schema, remediation and retest rule. The Cartesian product may produce candidate controls; prune duplicates and impossible combinations, document N/A rules, and version the registry. Publish counts for defined, applicable, executed, passed, failed, blocked, not-run and not-applicable controls. Never advertise “1,000 controls passed” from a matrix definition.

Examples:
- Evidence × Fact Lock × Provenance: source hash + scope + human review.
- Prompt × Prompt Preflight × Red-team: indirect prompt injection test and exfiltration oracle.
- Renderer × Code Lock × Capability: reject target-specific code if runtime/version is unknown.
- Visual × Visual Lock × Regression: compare canonical reference drift against defined threshold.
- QA × Release Gate × Human Signoff: authorized, hash-bound approval record.

## 8. Change-impact and invalidation

Represent dependencies as a directed acyclic graph. Each artifact records upstream IDs and exact versions/hashes. When an upstream dependency changes:
1. calculate transitive dependents;
2. mark affected locks/artifacts `STALE` or `INVALIDATED`;
3. identify the minimum required rebuild set;
4. rerun affected validators and regression tests;
5. preserve superseded artifacts and audit history;
6. require reapproval where the changed dependency affects a previously approved domain.

Examples: source correction invalidates linked claims, screenplay lines, scenes, overlays, prompts, manifests and approvals; character-canon change invalidates affected scene references and continuity QA; renderer-version change invalidates capability, code and render evidence, but not clinical facts.

## 9. Capability registry and renderer routing

Capabilities are operation-specific, not platform-wide. Record provider/tool, operation, exact version/model, environment, permission, checked_at, evidence, constraints and expiry/recheck policy. Distinguish `AVAILABLE`, `VERIFIED`, `UNAVAILABLE`, `NOT_TESTED`, `BLOCKED` and `EXPIRED`.

Do not generate target-specific executable code if target/version/schema is unknown. A provider-neutral manifest or pseudocode may be returned with an explicit non-executable label. Remotion/React TSX remains a candidate adapter; the existing static shim check and FFmpeg smoke sample do not establish actual Remotion runtime compatibility.

## 10. QA, release and measurable metrics

Every test result must include `test_id`, control/requirement IDs, oracle, expected result, observed result, threshold, environment, tool/version, timestamp, evidence URI/hash, status, defect IDs and reviewer where required.

Track at minimum:
- material claim verification coverage;
- source snapshot/hash coverage;
- applicable control execution coverage;
- prompt preflight pass rate;
- critical defect escape rate;
- character/visual regression score and threshold;
- frame/timing drift;
- actual render success rate with valid artifact evidence;
- accessibility defect and conformance status;
- rights/privacy coverage;
- cost per approved second and budget variance;
- approval completeness and latency;
- invalidation propagation completeness.

Metrics require denominators, inclusion rules and reporting windows. “100%” without denominator and applicability definition is invalid.

## 11. Cost, privacy, rights and resource governance

Set project-level budget ceilings, maximum retries, maximum asset size/duration, concurrency and timeout limits. Estimate before expensive calls; record actual costs only when measured. Stop or request approval when a ceiling is reached.

Collect minimum necessary personal data. Define retention/deletion and access scope. Track asset provenance, license/permission, territory, duration, attribution, modification rights, model training restrictions where known, and voice/likeness consent. Unknown rights status blocks publication of the affected asset.

Accessibility checks include captions/transcript quality, reading order, contrast, text size, motion sensitivity and non-audio comprehension, with the applicable standard and scope declared.

|---|---:|---|---|
| F0 Freeze & triage | 1–2 weeks | Remove unsupported renderer-ready claims; risk register; role matrix | Approved scope and risk owners |

Dates are planning targets, not delivery promises. Each phase requires owner, dependencies, budget, acceptance tests and documented residual risk.

## 13. Migration from V3

Preserve M00 + S01–S13 and Manifest V3 compatibility during migration. Introduce V4 contract envelopes and validators as an explicit schema version; do not silently reinterpret existing fields. Provide a migration map, fixtures, backward-compatibility tests and rollback plan. Do not label the package “V4 production-ready” until the implementation and required tests—not merely this specification—pass.

## 14. Release truth and current baseline

At the V3.0.5 audit baseline:
- plugin source inventory/read-back is verified; plugin remains private;
- local automated suite reported 31 passing tests in the prior validation record;
- the acceptance-case catalogue is not equivalent to all tests having run;
- ChatGPT live plugin invocation was NOT RUN;
- actual Remotion package installation/Studio/bundle/render was BLOCKED or NOT RUN;
- Remotion MP4 artifact QA was NOT RUN;
- no external AI video model was selected or tested.

These states must be preserved until new evidence exists. GitHub documentation/CI passing does not establish host runtime, clinical approval, external model behavior or video artifact quality.

## 15. Definition of done for M00 v4.0

M00 v4.0 is implemented only when:
1. versioned schemas exist for claims, sources, scenes, manifest, capabilities, controls, tests, approvals and audit events;
2. validators enforce schema plus cross-record semantics and dependency integrity;
3. gates enforce fail-closed transitions;
4. prompt firewall and red-team tests cover untrusted asset instructions;
5. capability routing blocks unsupported target code;
6. change-impact invalidation is tested;
7. human approvals are role-authorized and hash-bound;
8. control registry reports applicability and execution honestly;
9. CI executes deterministic tests and retains evidence;
10. release report distinguishes static, integration, runtime, render and human approval.

Until these conditions are met, the status is **SPECIFICATION / IMPLEMENTATION IN PROGRESS**, not production-ready.
